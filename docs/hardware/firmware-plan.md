# AI Passport 固件迁移与资源方案

核验日期：2026-10-30。状态：用户已确认全离线方向并授权 V1 代码实现，当前实现与验证边界见 [V1 说明](offline-v1.md)；下文保留资源预算与设计依据。只读检查现有源码、配置、资源元信息及厂商资料；未编译、烧录、跑自动化测试或修改固件/素材。体积和帧率目标不是实测承诺。

## 结论与建议

建议继续使用现有 ESP32-C3 AI Passport：保留待机、装备、九个符文、地图、全量图鉴和双语冒险日志的功能结构，优先删减全屏特效、资源分辨率和同时播放的声部，不先删除内容入口。固件采用 ESP-IDF + LVGL 原生实现，不嵌入浏览器，也不逐行翻译 HTML/CSS。

当前约束下可争取完整的功能与视觉主题，不能保证原型全部图片清晰度、过渡特效和帧率。第一阶段离线运行、不加硬件、不常驻 Wi-Fi/BLE、不要求 OTA；这些是建议默认值，不是已经确认的新产品要求。相册仍按既有约定单独讨论。

## 已核实的硬件与证据边界

- 厂商公开能力契约与本地配置一致：ESP32-C3、8MB Flash、无 PSRAM、240×320 屏与三个物理按键。项目横屏为 320×240。芯片为单核 RISC-V、最高 160MHz，400KB SRAM 中有 16KB 用于缓存；不能把 400KB 当成可分配堆。[芯片资料](https://documentation.espressif.com/ESP32-C3_Datasheet_en.pdf)、[厂商能力契约](https://github.com/FoloToy/ai-passport#hardware-capability-contract)。没有读取这台设备的芯片信息，本轮结论基于厂商契约和仓库设置，不等于现场识别板卡。
- 本地引脚权威来源为 [bsp_pins.h](../../firmware/components/bsp/include/bsp_pins.h)：屏幕 SPI2，MOSI 9 / SCLK 8 / CS 1 / DC 20 / 背光 21；三键共用 GPIO0 ADC；I2C SDA 10 / SCL 7；ES8311 与 CW2017 共用 I2C；I2S MCLK 6 / BCLK 5 / WS 3 / DOUT 2 / DIN 4。方案不新增引脚定义。
- 厂商 README 写 SPI 40MHz，详细指南及本地 BSP 写 80MHz，不能把仓库中的稳定运行注释当成本轮验证。按 40MHz 保守设计；以后比较 40/80MHz 的花屏、耗时和音频并发。来源：[README](https://github.com/FoloToy/ai-passport#hardware-capability-contract)、[硬件指南](https://github.com/FoloToy/ai-passport/blob/main/docs/hardware-design/AI_HARDWARE_DEVELOPMENT_GUIDE.md)。
- 板上 NTAG213 是被动 NFC 标签，无 MCU 读取 API，不能承担 amiibo 读卡。当前公开 BSP 也没有摄像头、GPS、触摸或外接存储接口；相机、感应器、amiibo 继续做游戏内模拟。不能从芯片支持 SPI 推断当前板卡可以直接加 SD 卡。厂商指南与 README 在低功耗唤醒描述上也存在差异，需后续按板卡和 BSP 核实。
- ES8311 可播放 PCM，CW2017 可提供电量与电压；电量不可硬编码为 99%，异常显示未知状态。独立电源键不是 ADC 三键。续航、扬声器听感、按键唤醒和准确校时均未实测，不给出续航小时数。

## 当前固件不是原型的完整实现

以 [main/CMakeLists.txt](../../firmware/main/CMakeLists.txt)、[slate_app.c](../../firmware/main/slate_app.c)、[game.h](../../firmware/main/game/game.h) 为准：现有页面没有完整装备和地图路由，纯 C 游戏枚举仅五类，图鉴 SUBJECT_COUNT 为 5。必须增加页面、扩展数据与状态机，不能仅换图。

可复用 BSP、LVGL 页面生命周期、输入代际隔离、NVS 进度框架、音频工作任务；五关旧模型只能作参考。新增圆/方炸弹独立状态、重做后的磁力/静止器规则，以及摩托、amiibo、感应器等，以当前原型行为为迁移基线。现有音频取消仅清空队列，无法中断正在播放的 PCM；静音也不检查正在播放的采样循环，后续必须修正。

[组件声明](../../firmware/components/bsp/idf_component.yml) 为 ESP-IDF >=5.5.3,<5.6、LVGL ^9.5.0、esp_lvgl_port 2.9.0。移植时应解析并锁定实际组件版本，不能因删除旧缓存而假定环境已经可用；不要直接合并厂商更新覆盖项目 BSP。

## Flash：先用好已经存在的空间

8MB 按 8MiB（0x800000）计算。现有 [partitions.csv](../../firmware/partitions.csv) 的 factory 从 0x10000 起占 4MiB，结束于 0x410000；尾部 0x3F0000 = 3.9375MiB 未分配。

建议第一版保持 factory 的大小与偏移，新增只读资源 data 分区，范围 0x410000–0x800000。这是方案草案，不在本轮修改分区表。资源独立于 app 生成一份带版本、长度、CRC、条目索引的 pack，使用 esp_partition_read 或受控 mmap 读取；不是将所有 PNG 转为 C 数组挤入 4MiB app。当前分区允许 app 内放字体和只读文本。

资源 pack 预算上限 3.9375MiB，建议初始包络：

- 九项场景：约 0.97MiB。按每张 320×176 RGB565 估算，共 1,013,760 字节；共用部分可再减少，不含 UI 外框。
- 共享人物、物体与特效精灵：0.30MiB。
- 394 条图鉴的照片/装备共用图：1.10MiB。相当于每条平均约 2.9KiB，不是现有图片已经达到的大小；离线压缩和质量验证是硬门槛。
- 地图瓦片与低清总览：0.45MiB。预算允许地图完整覆盖与全部 177 个现有命名点，不承诺原图级细节。
- 音效：0.55MiB。主方案为 16kHz 单声道 IMA ADPCM 流式解码，重要短旋律可用 22.05kHz；采样率统一到设备播放率时需离线重采样或独立格式切换，不能直接以错误频率播放。
- 图形 UI、徽记和公共纹理：0.15MiB。
- pack 索引、对齐和校验：0.10MiB。
- 上述合计约 3.62MiB，预留约 0.32MiB。预算是目标分配，尚无实际压缩包；任一组超额都必须重估，不靠把“压缩率”写大解决。

app 建议以 <=3.5MiB 为阶段目标，留出余量；旧约 1.99MB 固件报告来自历史源码，不能据此认定新代码必能装入。全量中英文文本、字体和索引也须计入 app 或资源包，不能重复统计或漏计。实际 app 大小待以后获授权构建才能知道。

资源包缺失或版本不符时显示可读错误页，不继续解引用。完整升级应交付匹配的 app 和资源包，资源更新期间不可继续从正在擦写的 Flash 绘制/播放。新增资源分区不是 OTA；需要 Wi-Fi 双槽更新时，两个 app 槽会挤占空间，必须重新做布局与故障恢复设计。[分区规则](https://docs.espressif.com/projects/esp-idf/en/v5.5.3/esp32c3/api-guides/partition-tables.html)、[分区 API](https://docs.espressif.com/projects/esp-idf/en/v5.5.3/esp32c3/api-reference/storage/partition.html)。

## SRAM 与刷新：不做整屏浏览器合成

静态算术核对：全屏 RGB565 为 153,600B = 150KiB，ARGB8888 为 300KiB；全屏双 RGB565 为 300KiB。当前代码的 320×20 行双缓冲实际为 25,600B = 25KiB；源码注释约 19.2KB 不正确，不能据此算内存。

建议采用 20 行双 DMA 缓冲作为初始方案，内存不足可降为单缓冲；不分配整屏 ARGB 画布，不让九个页面同时常驻。游戏背景优先从 Flash 直接取 RGB565，角色使用小尺寸带 alpha 精灵；切页面释放该页面对象和缓存。

运行时新增缓冲建议预算：显示 25KiB，当前页图像/地图瓦片缓存 24–48KiB，音频解码与环形缓冲 8–16KiB。它们不是“总内存占用”，还要加 ESP-IDF、LVGL 对象、任务栈、静态区、驱动 DMA 和模型。至少保留 40KiB 空闲内部堆，记录最低水位和最大连续块；这两个指标都合格才接受。

不能把压缩 PNG 文件大小当成解码内存。LVGL 9.5 lodepng 实现先解码 ARGB8888，整屏已经约 300KiB，再叠加其他对象很危险；大 PNG 不走该路径。[对应源码](https://github.com/lvgl/lvgl/blob/v9.5.0/src/libs/lodepng/lv_lodepng.c)。图鉴 JPEG 限在 88–96px 小图；地图使用 64px 等小瓦片，限制解码缓存数量，实际解码器内存待选型验证。任何需要自定义分块解码的路径属于后续实现工作，不能假定 LVGL 默认就支持。

完整一帧 SPI 像素数据需 1,228,800 bit；40MHz 理想传输约 30.72ms，80MHz 约 15.36ms，均未计命令、软件绘制和总线等待。因此不承诺 60fps：菜单以响应及时为主，静态场景游戏目标 20–30fps，地图移动可 10–15fps；这些是验收目标，不是本轮成绩。原型全屏扫描线动画、反复大面积模糊/透明叠层、全屏闪光、连续缩放旋转应减少；保留选中框、少量光效、关键动作帧与完成反馈。摩托滚屏会扩大脏区，需要单独验证，必要时降到 15–20fps 并保持运动速度与帧率解耦。

## 素材处理方案

- 所有现有原图保留；在独立设备资源输出目录派生，禁止覆盖 Web 原型素材。
- 以最终 320×240 可见尺寸设计布局，先统一视角和脚底/落点锚点，再裁透明边；不把带大空白的高分辨率图集运行时缩到小屏。
- 背景保留游戏原素材或经确认的参考生成图；图标、人物、铁板、冰柱等仍为栅格资源。LVGL 控件只承担文字、焦点、列表和排版，不用代码重画游戏美术。
- 活动物体优先 RGB565A8 或调色板加透明度；先验证 LVGL 当前版本支持及混合代价。照片类图像使用小尺寸 JPEG；共用一份图鉴/装备图，不额外存两套分辨率相近的缩略图。
- 颜色、透明边、缩小后文字可读性必须人工查看；压缩不能让物体判定范围与可见轮廓脱节。素材质量包预算不达标时，先降低非焦点图尺寸和动画帧数，再考虑分批资源包；最后才讨论删除条目。

## 字体与双语

静态读取现有 HyliaSerifBeta-Regular.ttf 的 cmap，未发现本轮源码/数据中汉字的覆盖。原型数据与运行源码的汉字并集约 1,854 个，包含注释，不能直接当最终字库清单。现有固件只编了 Hylia 16/20/28，中文不能因此自动显示。

英文保留 Hylia；中文需有合法来源、实际含中文字形的字体。当前原型使用思源黑体 Medium 替代，并不是游戏提取中文字体。若坚持原版中文字体，需取得对应字库并核实许可与字形后再裁剪；不能承诺 Hylia 自带中文。该选择是待确认项，不擅自更换美术方向。

离线从真正展示的标题、正文、地名、提示语和数字符号提取字形，中文正文建议 14/16px 两档、标题复用或少量更大字形；4bpp 为初始候选。1,854 个字以每字 16×16×4bit 的理论位图算约 232KiB/档，未计字距索引、行高及压缩；不是实测字库大小。禁止运行时加载完整 OTF/TTF 或完整 Unicode CJK 字库。

## 各页面与九项符文的取舍

- 待机：保留 Zelda 标题、眼纹、启动操作，时钟必须来自有效时间源。第一版可手动校时；完全断电后时间不可假装准确。待机亮度可降低，深睡唤醒显示流程以后单独验证。
- 装备：保留分类、选择、装备/卸下、属性和说明。只创建当前可见槽位；图鉴与装备共用图片。林克外观采用少量预生成姿态，不要求任意装备组合都拼装出完整模型。
- 圆弹/方弹：保持不同运动与放置规则、遥控引爆、冷却；少量爆炸精灵，避免满屏透明爆炸图。
- 磁力：沿用最新原型的同视角铁板搭桥；OK 抓取自动抬升、▲▼ 搬运、OK 放下。保留高亮、磁力连接、落稳/倾斜、过桥反馈；不恢复轴向菜单和按键组合。
- 静止器：保留滚石运动、锁定、六次击打、角度与远射反馈；物理先用整数/定点或简单近似。C3 无硬件浮点单元，避免大量每帧三角/浮点计算；飞行镜头改为分段跟随也要保留远射距离感。
- 制冰：保留选五处落点、三根冰柱、升起/碎裂/替换和通过判定；人物用少数姿态和位置插值，避免单张站姿突然瞬移。
- 照相机：保留游戏场景取景、对焦和识别反馈；这是虚拟拍摄，不是硬件摄像。若以后做相册，优先记录场景 ID/物体布局/取景参数，按场景版本重放；不将 RGB 截图频繁写入 NVS。相册具体功能仍延后确认。
- 大师摩托：保留自动骑行、单键起跳、落地和失败/完成；跑道和车辆共用几帧，避免大面积全屏视差。跳跃碰撞与画面高度共用坐标，不能靠减素材大小掩盖错误。
- amiibo：保留模拟选择、读取、补给落下、开箱与收取；UI 明确是模拟，不能借板上被动标签声称能读取 amiibo。
- 感应器：保留选路、信号强弱、自动前进、发现神庙展开动画，以及与地图地点状态联动；不是 GPS 导航或真实环境探测。
- 地图：保留一张连续的海拉鲁全图、当前 177 个命名点、移动、地点信息和缩放。屏幕之外的数据用瓦片管理，不整张解码。缩放采用 2–3 档离线生成层级；仍按 OK 切换横移/纵移/缩放、▲▼ 执行。点位只创建视野内标记，不创建 177 个持续刷新的 LVGL 控件；不扩展成全克洛格/宝箱数据库。
- 图鉴：394 条文字与照片优先全部保留，每次只创建可见列表；详情照片约 88–96px，避免高分辨率图入 RAM。没有经过压缩质量验收前，不承诺全部原图等比例保真。
- 日志：保留原型现有 152 条含 DLC/联动、双语正文，按条目加载字符串和分页阅读；不把所有正文复制到堆。读完进度、任务完成、装备状态、神庙标记写 NVS，使用去抖和明确保存点，不在每帧写 Flash。
- 设置：真实亮度、音量、语言、静音、电量；扫描线建议静态轻纹理/可关闭，删除持续全屏重绘。游戏暂停和返回遵循相同三键规则。

## 音频：保留游戏旋律，改变编码与调度

本轮静态测量现有 botw 输出目录有 40 个 WAV（包含任务完成音的放大副本），合计 11,718,976B、约 62.09 秒；这不是整个下载包大小。22.05kHz/16bit/mono PCM 同时长仍约 2.61MiB；16kHz/4bit ADPCM 理论约 0.474MiB，另计块头和索引，能接近预算。最终烹饪完成旋律还需导入用户指定的正确文件，不能继续用任务完成音冒充。

建议短按、光标可优先无压缩 PCM；较长音效用独立块 ADPCM 解码到小缓冲，不整个加载。默认只播放一个高优先级声音；导航音可丢弃，爆炸/完成可抢占，磁力移动循环可被暂停、静音和返回真正中断。必要的双声部混音留待 CPU/音频测试决定，不能照搬浏览器六路播放。调整响度应统一校准并保留峰值余量，不对每个文件盲目乘 10。

## 分阶段落地与验收门槛

1. 先做离线资源预算和设备尺寸预览：列出每张图/每段音频/每组字形的最终尺寸、格式、字节数，核对 pack <=3.9375MiB，app 部分字体/文本另计。预览不改原型资产；需要人工确认视觉取舍。
2. 确认页面与状态表：九项完成/失败/重试/暂停、地图焦点与缩放、装备与日志的持久化，写清每个 UP/DOWN/短 OK/长 OK 的行为。
3. 以后另获授权才建立设备资源加载、双语字体、页面框架与音频抢占，先形成待机/目录/设置/文字阅读的小闭环，再逐项移植。资源文件与字体生成工具缺失的部分先恢复，不假定旧生成 C 文件等于可重建管线。
4. 再迁移九项玩法及地图/装备/图鉴/日志；优先磁力、静止器、摩托这三个高风险画面。纯逻辑状态和渲染分开，固定步长或累计时间更新，不使用帧数决定运动与成功。
5. 经用户另行授权后，才编译、进行主机自动化测试与设备性能验证。需要记录 app/资源实际大小、最低空闲堆、最大连续块、帧耗时分布、音频欠载、按键延迟；每页至少覆盖成功、失败、重试、长按退出和反复进入后的内存回收。

阶段验收目标：普通按键反馈 <=100ms；长按阈值统一沿用现有 550ms、消费短按；完成音只触发一次且可中断旧音；场景游戏争取 20–30fps，摩托和地图允许独立降档；最紧张场景至少 40KiB 空闲内部堆。具体性能与低功耗必须以后实机验证，不以旧报告或计划数值代替。

## 待确认事项
