## 目标与执行顺序

形成一份能从干净检出构建、能说明真实功能、能在设备和浏览器中复现的版本。保留当前目录主结构，先关闭功能缺口，再做小范围整理和文档包装，最后准备 GitHub Pages 与版本发布。

## 二、结构与代码整理

### 保留主目录，避免临发布大搬家

- `firmware/`：唯一 ESP-IDF 工程入口。
- `prototype/`：浏览器原型及交互。
- `assets/`：来源、原始材料、派生资源及电芯参数记录。
- `tools/`：资源生成、截图、校时等主机工具。
- `docs/`：使用、架构、验证与专题说明。
- `design/`：候选方案与设计资料，不作为设备运行资源入口。
- `screenshots/`：本地截图收件箱，精选文档图另行整理。

## 五、GitHub Pages 原型

### 建议方案

保留原型纯静态站，使用 GitHub Actions 组织一个独立发布目录，再部署到 GitHub Pages。发布物保留 `prototype/` 与其所需 `assets/` 的同级关系；根路径提供进入原型的入口。不要为了上线改变现有源码目录，也不要直接发布整个工作区。

### 准备与检查

- [ ] 确认实际远端、仓库可见性、Pages 权限和发布分支。当前本地记录有 origin，但没有 `.github/` 工作流目录；线上 Pages 是否开启仍待核实。
- [ ] 选择公开演示所需且可分发的图片、字体与声音，建立明确的发布白名单。
- [ ] 排除固件构建、资源包、原始解包材料、本地日志、下载残片、截图收件箱和未选设计稿。
- [ ] 核对仓库子路径下的相对 URL、文件名大小写、CSS 字体路径、哈希路由刷新与深链接。
- [ ] 检查原型借用 `assets/raw` 字体/Logo 及 `assets/gen/firmware` 文件的实际依赖，不能只复制 `prototype/`。
- [ ] 核对首次资源体积；当前原型中文字体为完整字库，应评估网页专用子集与许可保留，避免手机初次加载过重。
- [ ] 明确声音需要用户操作后启用，检查鼠标/键盘/触屏三键及手机布局。
- [ ] 区分可公开的演示素材和仅本地自备素材。资源不齐时，公开范围先由用户决定，不擅自用缺失图上线。
- [ ] 在发布前核对 GitHub 官方当前限制与工作流要求；本计划不把平台设置或站点地址视为已确认。

完成标准：经授权部署后，用仓库实际 Pages 地址访问；没有资源 404、子路径错误或刷新失效，README 有可点击链接。网站上线不等于固件已经通过实机验收。
